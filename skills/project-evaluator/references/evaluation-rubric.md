# 评估准则（Step 2 评级与计分）

评级只依据 Step 1 收集到的用户原话。任何维度都必须能回答：「这个评级基于用户说过的哪句话？」

计分：🟢 健康 = 2.0｜🟡 一般 = 1.2｜🔴 高风险 = 0.4。总分 = 五维之和（2.0 - 10.0），保留一位小数。
**信息未知的维度最高只能给 🟡**，并在理由中写明因缺少什么信息。

---

## 维度① 需求与市场

判断「这个问题真实存在，且有人愿意用」。

| 评级 | 判定标准（满足任意两条） |
|------|------------------------|
| 🟢 | 用户自己就是受害者且每天/每周都被这个问题困扰；能立刻说出 3 个以上真实使用者；已经有人用别的笨办法在解决（说明需求真实）；有人表达过付费意愿 |
| 🟡 | 需求听起来合理但没有验证；用户群体清晰但暂时接触不到；只有创造者自己需要（自用工具默认落在这里，且这是可接受的） |
| 🔴 | 说不清是谁的什么痛点；「我觉得大家应该会喜欢」但找不到任何一个具体用户；市场已有成熟免费方案且用户说不出差异化理由；需求依赖用户改变强习惯 |

常见误判提醒：自用工具不是缺点。若 S6 成功标准是「我自己每天在用」，则 🟡 即为正常，不要因「没有市场」而给 🔴。

---

## 维度② 方案与复杂度

判断「第一版能否收敛成一个做得完的东西」。

| 评级 | 判定标准 |
|------|---------|
| 🟢 | 能明确说出唯一的核心功能；MVP 功能 ≤ 3 项；功能之间不互相依赖；有清晰的「先做什么后做什么」顺序 |
| 🟡 | 功能 4-6 项且能分出优先级；有一两个功能技术含量偏高但可以延后；核心功能明确但边界模糊 |
| 🔴 | 功能 7 项以上且都说「必须有」；无法回答「只保留一个功能会留哪个」；第一版就包含多端（网页+App+小程序）、多角色（用户+商家+管理员）、实时协作、推荐算法等重型能力；描述里出现「像微信一样」「像抖音一样」的整体对标 |

复杂度加权提醒：以下能力对新手属于「隐形重活」，出现两项及以上时该维度不得高于 🟡——用户登录与账号体系、在线支付、文件/视频上传处理、实时消息、多角色权限、爬取第三方数据、离线同步。

---

## 维度③ 技术与资源

判断「以现有技术水平、时间和预算，能否撑到上线」。

参考基线（AI 辅助编程，非硬性规则，用于估算量级）：

| 技术水平 | 3 项功能内的简单 MVP 大致所需投入 |
|---------|-------------------------------|
| 完全不会写代码，全靠 AI | 40-80 小时，需要额外时间学部署与排错 |
| 看得懂能改 | 25-50 小时 |
| 会写但没独立完成过 | 15-35 小时 |
| 有完整项目经验 | 10-20 小时 |

| 评级 | 判定标准 |
|------|---------|
| 🟢 | 可投入时间 ≥ 估算工时的 1.5 倍；产品形态与技术水平匹配（如纯前端网页 / 本地脚本）；预算覆盖必需开销；无需申请难拿的资质或接口 |
| 🟡 | 时间勉强够（0.8-1.5 倍）；预算紧张但可用免费额度撑住；形态偏难（如原生 App）但可换成更简单的形态；依赖的接口需要申请但普遍能通过 |
| 🔴 | 可投入时间明显不足（< 估算工时的 0.8 倍）且有硬截止；0 预算却需要持续付费的 AI 接口/服务器/短信；需要企业资质、支付牌照、特殊备案而用户不具备；技术形态与水平严重错配（如零基础做原生 iOS + 后台管理系统） |

时间估算写法：报告中只给量级区间与依据，例如「按每周 5 小时、需约 40 小时，约 8 周」，不要伪造精确数字。

---

## 维度④ 风险与依赖

判断「有哪些会让项目直接停摆的东西」。

| 评级 | 判定标准 |
|------|---------|
| 🟢 | 不依赖外部平台的非公开数据；不涉及敏感个人信息；单人可独立完成全部环节；失败成本低（时间以外几乎无损失） |
| 🟡 | 依赖 1-2 个稳定的公开服务（如常见 AI 接口、地图接口）；有一定合规注意事项但可规避；需要他人配合但对方已知情 |
| 🔴 | 核心依赖爬取或抓取第三方平台数据（随时可能被封禁或涉及违规）；处理身份证、医疗、金融等敏感信息；需要牌照或行政许可；关键环节依赖尚未答应的合作方；单一接口一旦涨价或下线项目即归零 |

必须主动检查的高风险清单：抓取第三方数据、代下单/代抢票、个人隐私数据、医疗健康建议、金融投资建议、二次分发受版权保护的内容、未成年人相关服务。命中任意一项，该维度不得高于 🟡；构成明确违法违规的，直接 🔴 并在报告中给出合法替代方向。

---

## 维度⑤ 成功标准

判断「成功的定义是否具体、可衡量、可在期限内验证」。

| 评级 | 判定标准 |
|------|---------|
| 🟢 | 成功标准具体可验证（如「我自己连续用两周」「10 个真实用户」「收到第一笔 9.9 元」）；与资源投入相匹配；有大致时间点 |
| 🟡 | 有方向但不好衡量（如「用起来还不错」「有点用户」）；标准合理但时间点缺失 |
| 🔴 | 说不清什么算成功；标准与资源严重不匹配（如每周 2 小时却要求三个月内一万用户）；成功完全依赖不可控外部因素（如「被平台推荐」「爆火」） |

---

## 覆盖规则（优先于总分）

1. 存在任一 🔴 维度时，最终建议**不得**为「强烈建议启动」，最高只能是「建议调整后启动」。
2. 命中明确违法违规的阻断项时，无论总分多少，最终建议一律为「强烈建议放弃（或彻底换方向）」，并给出合法替代路径。
3. 维度③为 🔴 且用户有硬性截止时间时，最终建议中必须包含「缩小范围」或「延长周期」的二选一。
4. 未知槽位 ≥ 3 个时，在总体评分后标注「（信息不足，仅供参考）」。
5. 项目定位为练手/学习（S6 选择「学会某项技能」）时，维度①按「自用工具」标准评价，不因缺乏市场而给 🔴。

## 分数与建议对照

| 总分 | 最终建议 |
|------|---------|
| ≥ 7.5 且无 🔴 | 强烈建议启动 |
| 4.0 - 7.4，或分数达标但存在 🔴 | 建议调整后启动（必须写明调整什么） |
| < 4.0，或命中阻断项 | 强烈建议放弃或彻底换方向（必须给 1 条保留价值的替代做法） |

## 常见风险模式速查

| 模式 | 典型信号 | 建议方向 |
|------|---------|---------|
| 范围失控 | 第一版就要全平台、全角色 | 砍到单一平台 + 单一角色 + 1 个核心功能 |
| 空中楼阁 | 找不到任何一个具体用户 | 先手动服务 3 个真实用户一周，验证需求再动手 |
| 依赖爆雷 | 核心数据靠爬别人的站 | 改为用户自己录入或使用官方开放接口 |
| 无限期项目 | 没有截止时间也没有成功标准 | 设定 2 周的第一个可见成果（Demo 或截图） |
| 成本失控 | 0 预算 + 大量 AI 调用 | 限制调用频次、改用小模型、或让用户自带 API Key |
| 完美主义 | 上线前要求界面精美、功能齐全 | 先做能跑通的丑版本，交给 3 个人试用 |
